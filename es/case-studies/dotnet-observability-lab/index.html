Problema

Aceptar una escritura, consolidarla después y preservar la integridad ante las fallas.

Una API recibe un valor y debe almacenarlo de forma persistente e idempotente. Otro servicio debe consolidar ese valor de manera asíncrona, sin llamadas HTTP entre las API y sin que una nueva entrega del broker duplique los efectos de negocio.

La dificultad no está en el valor decimal, sino en coordinar la persistencia, publicación, recepción, confirmación y recuperación, incluso cuando no sabemos con certeza si una etapa terminó.

Restricciones y atributos de calidad

Las decisiones comienzan por aquello que debe seguir siendo verdadero ante una falla.

01

Sin llamadas directas entre API

La ingesta y la consolidación son límites independientes. La lectura no debe depender de la disponibilidad de la API de escritura.

02

Entrega de al menos una vez

RabbitMQ puede volver a entregar mensajes. Los duplicados forman parte del contrato y deben tratarse como un comportamiento normal.

03

Estado persistente como fuente de verdad

PostgreSQL protege la idempotencia, Outbox, Inbox y el agregado. Redis es solo una optimización opcional que no determina la integridad de los datos.

04

Observabilidad independiente de la plataforma

OpenTelemetry permite generar trazas, métricas y registros. Aspire compone y muestra el entorno local, pero no enruta el tráfico de negocio.

Decisiones y trade-offs

Los patrones responden a escenarios de falla concretos.

Mensajería asíncrona en lugar de una llamada síncrona

RabbitMQ desacopla la disponibilidad y la latencia entre la ingesta y la consolidación.

Costo asociado: consistencia eventual y mayor complejidad operativa.

ADR 0004 ↗

Transactional Outbox

El valor y el evento pendiente se persisten en la misma transacción; un worker lo publica después con confirmación del broker.

Costo asociado: consultas periódicas, reintentos, cuarentena y posibilidad de publicar un mensaje más de una vez.

Implementación ↗

Inbox persistente en el consumidor

La identidad del mensaje y la actualización del agregado se confirman en la misma transacción PostgreSQL.

Costo asociado: cada mensaje nuevo requiere persistencia y una política de retención a futuro.

Implementación ↗

At-least-once + idempotencia

El diseño no promete exactly-once. Hace que la repetición sea segura para el efecto de negocio.

Costo asociado: cada consumidor debe gestionar explícitamente la identidad de los mensajes y los duplicados.

Contrato del evento ↗

PostgreSQL como fuente de verdad y Redis opcional

El caché reduce el costo de la repetición HTTP, pero una caída, una expiración o la expulsión de datos de la caché no pueden comprometer la integridad.

Costo asociado: cuando no hay datos en caché o esta falla, las consultas pueden llegar a la base de datos.

ADR 0003 ↗

OpenTelemetry como estándar

El contexto W3C cruza el límite asíncrono; Aspire es una de las superficies locales de inspección.

Costo asociado: hay que mantener explícitamente la propagación del contexto y la instrumentación.

ADR 0005 ↗

Fallas relevantes

La propiedad interesante del diseño aparece cuando se rompe la ruta nominal.

Solicitud HTTP duplicada

La misma clave y el mismo valor devuelven el comprobante original; un uso conflictivo devuelve 409. La restricción única en PostgreSQL resuelve la carrera concurrente.

Mensaje entregado nuevamente

Inbox evita que se repitan los efectos de negocio. El mensaje puede consumirse más de una vez sin volver a incrementar el agregado.

Broker no disponible

La API todavía puede aceptar y persistir la escritura. Outbox mantiene el trabajo pendiente para publicarlo después.

Redis no disponible

Se pierde la vía de acceso rápido, pero se preserva la integridad. La decisión de idempotencia vuelve a PostgreSQL.

Publicación confirmada, transacción sin completar

El evento puede volver a publicarse con la misma identidad; el consumidor trata el duplicado de forma segura.

Falla en la consolidación

La transacción revierte tanto el registro de Inbox como la actualización del agregado. No queda un marcador falso de procesamiento concluido.

Observabilidad

El diagnóstico debe atravesar el mismo límite que atraviesa el negocio.

El contexto W3C iniciado en la solicitud se almacena junto con Outbox; el worker de publicación lo retoma y lo propaga mediante encabezados AMQP hasta el consumidor. Las métricas de baja cardinalidad diferencian aceptación, publicación, procesamiento y duplicación; los registros estructurados documentan los resultados operativos relevantes.

El objetivo no es simplemente tener paneles de control. Es poder explicar por qué una escritura todavía no apareció en el modelo de lectura y localizar el límite donde el flujo está detenido o repitiéndose.

Límites deliberados

Una arquitectura de referencia no es una receta para producción.

El laboratorio mantiene un único PostgreSQL local con bases de datos lógicas separadas, no define una plataforma de despliegue para producción y no implementa en v1 una política completa de reintentos limitados y cola de mensajes fallidos (DLQ) en el consumidor. Tampoco promete ordenamiento de eventos ni exactly-once.

Estos límites son parte de la evidencia: muestran qué se decidió, qué se simplificó con fines educativos y qué decisiones deberían reabrirse en un sistema real.

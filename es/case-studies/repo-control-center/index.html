Estudio de caso arquitectónico · observabilidad de ingeniería

Observar decenas de repositorios sin tener que mantener otro backend.

El Repo Control Center nació de un problema operativo sencillo: a medida que crece el número de repositorios, la integración continua, las entregas, las versiones publicadas, la seguridad, los paquetes y la actividad quedan repartidos entre distintas secciones y API de GitHub. La solución recopila estos datos fuera del navegador, indica cuándo la información está incompleta y publica una instantánea estática (snapshot) para su consulta.

Abrir Repo Control Center ↗Explorar repositorio ↗

El panel es de solo lectura. Los tokens utilizados para recopilar datos permanecen en GitHub Actions y nunca llegan a la aplicación web publicada.

Problema

GitHub reúne las señales, pero no ofrece una visión operativa del conjunto de repositorios.

La compilación, los despliegues, las versiones publicadas, la actividad, las alertas, los paquetes y los elementos pendientes se consultan en distintas secciones y API. Revisar cada repositorio por separado funciona cuando son pocos; a mayor escala, reunir el contexto se convierte en una tarea costosa.

El desafío no consistía en crear otro panel de control. Era construir un lenguaje común para interpretar el estado de los proyectos sin convertir la ausencia de datos en una falla ni requerir infraestructura permanente solo para agregar señales que cambian con poca frecuencia.

Restricciones y atributos de calidad

La arquitectura parte de la confianza de los datos y del costo operativo aceptable.

01

Sin servidor de aplicación permanente

La recopilación se ejecuta en GitHub Actions y genera una instantánea JSON que se publica mediante GitHub Pages.

02

Sin credenciales en el navegador

La aplicación web consume únicamente datos estáticos. Los tokens y permisos quedan restringidos al entorno de automatización.

03

Los datos incompletos son un estado válido

Cada repositorio indica si la recopilación fue completa, parcial o no estuvo disponible, junto con un nivel de confianza basado en la cobertura de las fuentes.

04

Una falla aislada no interrumpe el conjunto

Las consultas opcionales pueden fallar sin impedir la publicación del resto del portafolio, y esa pérdida de información queda identificada.

Decisiones arquitectónicas

El diseño separa la recopilación con permisos especiales, el contrato de datos y la presentación pública.

GitHub Actions como proceso de recolección

El recolector en Node.js consulta las API durante el flujo de trabajo, pagina los resultados, limita la concurrencia y normaliza los datos antes de publicarlos.

Costo asociado: la actualización es periódica, no en tiempo real.

Instantánea estática como contrato de lectura

El JSON publicado evita que la aplicación web dependa de API autenticadas y establece un contrato de lectura reproducible.

Costo asociado: el estado mostrado representa el último workflow exitoso.

Angular SPA en GitHub Pages

La interfaz ofrece filtros, búsquedas, detalles por repositorio y una visión consolidada sin necesidad de mantener un servidor en ejecución.

Costo asociado: las rutas detalladas usan hash y el contenido depende del snapshot publicado.

Separar la confianza en los datos del estado del repositorio

complete, partial y unavailable describen la observabilidad de la recolección; la salud del repositorio sigue siendo una clasificación distinta.

Costo asociado: la UI necesita comunicar incertidumbre en vez de resumir todo en un único color.

Clasificación semántica de workflows

CI, quality, security, mutation, delivery, release, Pages y maintenance cumplen funciones distintas; solo la señal correcta debe influir en build y delivery.

Costo asociado: las heurísticas necesitan un override cuando los nombres no expresan la intención.

Seguridad basada en evidencia, no en una puntuación simplificada

Dependabot, code scanning, el workflow de seguridad y OpenSSF Scorecard se presentan por separado. La falta de acceso reduce la confianza, no se convierte en una afirmación de seguridad.

Costo asociado: la lectura es más honesta, pero menos simplificada.

Trade-offs y límites

Reducir la infraestructura desplaza complejidad al contrato de datos y a la interpretación de las evidencias.

No es tiempo real

La tarea programada actualiza los datos aproximadamente una vez por hora. Esto es suficiente para el mantenimiento del portafolio, pero no reemplaza el monitoreo operativo de producción.

No todo delivery es observable

Los deployments externos a GitHub pueden no aparecer; la versión queda vacía cuando no existe una asociación confiable con la entrega.

Los permisos afectan la cobertura

Actions, Deployments y alertas de seguridad pueden exigir permisos adicionales. La ausencia se informa como pérdida de confianza.

Un snapshot no es una serie histórica

Las métricas de 30 días se calculan nuevamente a partir del estado disponible. Una tendencia temporal exige persistir snapshots anteriores.

Las heurísticas tienen límites

Los nombres de workflows fuera de las convenciones pueden quedar como desconocidos. La configuración de cada repositorio permite ajustar explícitamente la clasificación.

GitHub Pages impone límites

La aplicación no controla algunos encabezados HTTP ni ciertos comportamientos del alojamiento, que dependen de la plataforma.

Lectura arquitectónica

La observabilidad de ingeniería también necesita modelar la incertidumbre.

La principal lección del proyecto va más allá de crear un panel de control. Consolidar señales de ingeniería exige preservar la diferencia entre ausencia, falla de recolección, evidencia negativa y evidencia positiva. Sin eso, una interfaz sencilla puede producir una interpretación incorrecta del portafolio.

Al hacer explícitas la cobertura y la confianza, Repo Control Center trata la calidad de la propia observación como parte del dominio: una decisión que reduce diagnósticos falsos y mantiene útil la solución incluso cuando no todas las fuentes están disponibles.
